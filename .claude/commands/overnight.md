# Overnight run

The user typed this command and left. Nobody watches this run, and the user reads its result on a phone, where no prompt can be answered. This command is the user's own message, so it starts the `## Unattended run` rules of each repo's `docs/agents/workflow.md`. Where this file and that section differ, this file wins. The user's line is `$ARGUMENTS`, and a rule in the line wins over this file.

## Rules for the whole run

- **No questions.** Do not use AskUserQuestion, do not ask in prose, and do not end a turn with a question. A Stop hook blocks a turn that ends with a go-ahead question. Where a command, a skill or a workflow file says to ask the user, or to stop and wait for an answer, take the recommended option and continue.
- **Decision log.** Write each choice as one row in `~/tmp/<YYYY-MM-DD>-overnight/decision-log.md`, where the date is the day the run starts. Make the file at the start, with the header `| Time | Repo | Choice | Reason | Evidence |`. The evidence is a command output, a `file:line` or a URL. In a repo with a GitHub tracker, also post the choice with `agent-skills decide`, as the Choices rule of `## Unattended run` says. Each subagent prompt below names the log path, and the subagent adds its own rows.
- **Merge.** `agent-skills land <pr>` is the only way to merge. Never run `gh pr merge`. Only this session runs `land`: a subagent never merges.
- **Review.** A reviewer subagent that did not write the code at the PR head posts the review decision. This session never posts a review decision, because it does not review.
- **One item at a time.** Work on one pull request or one source issue at a time in each repo, because `land` moves the checkout to the base branch.
- **Stop.** Stop only when the queue of every repo is empty, or every item that remains is blocked. Do not stop early.

## Steps

1. **Pick the repos.** When the line names folders under `~/code`, the run covers those repos, one after the other, in the order of the line. Otherwise it covers the repo of the current folder. A repo is **local-only** when it is `osrs-shorts` or `osrs-handoff`, or when it has no `origin` remote on GitHub. A local-only repo never pushes and never gets a pull request, and the run adds no remote to it.
2. **Pre-flight each repo**, before any work in it. `agent-skills doctor` exits 0, and `docs/agents/workflow.md` has a `## Checks` heading and a `## Unattended run` heading. When a check fails, skip the repo and write the reason in the decision log and in the final message. In a repo that passes, read all of `docs/agents/workflow.md`.
3. **Read the queue.** Run `agent-skills next` in the repo root and read its whole output. When it exits 2 because the repo is in files mode, or the repo is local-only, the queue is the open pull requests that `gh pr list --repo <owner>/<repo>` shows (none in a local-only repo), then the unchecked tasks of `tasks/todo.md`.
4. **Land the pull requests that are ready.** Take each pull request that the queue lists for review and that is not a draft. Check out its branch with `gh pr checkout <pr> --repo <owner>/<repo>`, then review it (step 7), wait for CI (step 8) and land it (step 9).
5. **Build the tasks marked `ready-for-agent`.** Take each source issue or single task that the queue lists for build, and start one `general-purpose` subagent for it. Its prompt is:
   1. "Nobody watches this run. Do not ask the user anything. For each choice, take the option you recommend, and add a row to the decision log `<log path>`: time, repo, choice, reason, evidence."
   2. "Read `${CLAUDE_PLUGIN_ROOT}/.claude/commands/build.md` in full, and follow it for `<n>` in the whole-plan mode. Where it says to ask the user, take your recommended option. Stop when the pull request is open and `agent-skills evidence <pr>` exits 0, or in a local-only repo when the tasks are committed on the branch. Do not start the review subagent, and do not run `agent-skills land` or `gh pr merge`."
   3. In files mode: "Build the unchecked tasks of `tasks/todo.md` on one branch." In a local-only repo, add: "Commit on the branch, push nothing and open no pull request."
   4. "Return: the PR URL or the branch, the tasks you built and the ones you left out, your choices, and any blocker."

   A task without the `ready-for-agent` label, and the tasks it blocks, stay out of the build. In files mode, every unchecked task of `tasks/todo.md` counts as ready. List them in the final message. When the subagent returns a blocker, write it in the decision log and go on with the next item. Otherwise review the pull request (step 7), wait for CI (step 8) and land it (step 9).
6. **Plan only when the line asks.** Issues that the queue lists for spec, plan or refine get a spec or a plan only when the line asks for one. Then run those stages as the Stages rule of `## Unattended run` says, and build the plan in the same run (step 5). Otherwise list the issues in the final message.
7. **Review.** Start one `agent-skills:code-reviewer` subagent. Its prompt is:
   1. The whole output of `agent-skills brief review <pr>`, which names the task issue, the PR, the spec and the standard.
   2. "Read the spec and the standard named above in full before you review."
   3. "Nobody watches this run. Do not ask the user anything. Review the PR branch across correctness, readability, architecture, security and performance. Label each finding Critical, Required, Optional, Nit or FYI. Check each acceptance criterion of the task. Apply each finding whose fix fits in one session, with your recommended option when it has several fixes, unless the user's line lists it as a step that waits for the user. Add a row to the decision log `<log path>` for each option you chose. Run the checks with `agent-skills run --`, then commit and push. When you applied no finding and no Critical or Required finding is left, tick the met criteria with `agent-skills ac <task> --tick <list>`, and post the review decision with `agent-skills decide <task> --from review --pr <pr> --reviewer 'agent-skills:code-reviewer subagent'`, with the body on stdin: the guesses under `#### Guesses and gaps`, or 'No findings and no decisions.' When the pull request closes no issue, post it on the pull request: `agent-skills decide <pr> --from review --pr <pr> --reviewer 'agent-skills:code-reviewer subagent'`. Do not run `agent-skills land` or `gh pr merge`. Return: the URL of the decision comment, if you posted one; the findings you applied, with the option you chose; every other finding with `file:line`, what is wrong and what happens if it stays; and the acceptance criteria that are met and not met."

   When the reviewer applied findings, it posted no decision, because it wrote code at the new head. Start a new reviewer subagent with the same prompt and the commits after the last review. Stop after three reviewer subagents for one pull request: leave it open and report it. When a finding that nobody applied is Critical or Required, leave the pull request open and report it. For a lower finding that nobody applied, file a follow-up issue with `gh issue create --repo <owner>/<repo>`, write it in the decision log and go on. In a local-only repo, write it only in the decision log. A push after the decision needs a new review, unless the patch-id of the PR change is unchanged.

   In a local-only repo there is no pull request. The reviewer prompt names the branch and the base branch instead of the `brief` output, and the reviewer reviews the branch against the base branch and commits its fixes without a push. When it applied no finding and no Critical or Required finding is left, it records the review with `agent-skills decide --from review --local --reviewer 'agent-skills:code-reviewer subagent'`, with the body on stdin. That command commits `docs/reviews/<branch>.md` on the branch. The rules for a new round are the same as for a pull request.
8. **Wait for CI.** A local-only repo has no CI, so skip this step there. `land` does not read CI. When the CI line of `## Unattended run` says that CI runs on each pull request, wait for the run on the PR head with `gh pr checks <pr> --repo <owner>/<repo> --watch` before `land`. When a check fails, rerun it once with `gh run rerun <run-id> --failed --repo <owner>/<repo>`. When it fails again, and the same check also fails on the last run of the base branch (`gh run list --repo <owner>/<repo> --branch <base> --workflow <workflow> --limit 1`), write it in the decision log as a flake and go on to `land`. When the pull request has no checks, or a run cannot start, write that in the decision log and go on to `land`. Otherwise start a build subagent to fix the failure and review again (step 7), or leave the pull request open and report it.
9. **Land.** Run `agent-skills land <pr>` on the PR branch, from this session. When it exits 1, fix what it names and run it again, or leave the pull request open and report the reasons. When it refuses because the branch is behind its base, merge `origin/<base>` into the branch, push and run `land` again: the patch-id stays the same, so the review decision still holds. When that merge has conflicts, start a build subagent to resolve them, then review again (step 7). Exit 2 with "is merged, but the checkout is not synced" means that the merge is done: write the message in the report, and do not run `land` again. In a linked worktree, `land` removes the worktree, so change to the folder it names before the next command.

   **Local-only repo:** run `agent-skills land --local` on the branch, from this session. It runs the `## Checks` commands, merges the branch into the base branch with a merge commit, and deletes the branch. It never fetches or pushes. When it refuses because the branch is behind its base, rebase the branch onto the base branch and run it again: the patch-id stays the same, so the review file still holds. When the rebase has conflicts, start a build subagent to resolve them, then review again (step 7). Exit 2 means that the merge is done and the checkout is not synced: write the message in the report, and do not run `land --local` again. In a linked worktree, `land --local` removes the worktree, so change to the folder it names before the next command.
10. **Loop.** After each item, run `agent-skills next` again, because a merge can unblock tasks. Go back to step 4 until the queue of the repo is empty or every item in it is blocked. Then go to the next repo.
11. **Report.** The final message gives, per repo: the pull requests that landed, with their URLs; what is open and why; the repos that were skipped and the issues that were not planned. Then it gives the decision log path and what was not verified. It holds no question and no offer.
